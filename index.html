The 60-Second Response That Should Have Taken Nanoseconds

A customer at work reported that a web service generated by our product was taking 60 seconds to respond. For context, our product generates web services from legacy COBOL applications — a request comes in as JSON or SOAP, a runtime engine translates it into a format the COBOL application can process, then translates the output back. Normal response times are milliseconds at worst. Sixty seconds meant something was broken.

I recreated the issue locally, confirmed the latency, and built a trivial control service to verify the platform itself was fine. It was — nanoseconds. So the problem was specific to this service.

I pulled up Wireshark to inspect the raw HTTP traffic. The request body had an array initialized with 100 null elements. The response was worse — 1,000 nulls. A lot of memory allocated for nothing.

The root cause came down to how the generated code handled memory pre-allocation for arrays inside loops. COBOL doesn't support dynamic allocation, so everything has to be sized up front. The generated code was over-allocating based on worst-case defaults, and the runtime was faithfully serializing all that empty space into every response. Multiply that across nested structures and you get your 60-second round trip.

I tuned the pre-allocation logic to size arrays based on actual usage. Response times dropped back to nanoseconds, wasted memory disappeared, and the fix shipped to all customers on the product.

Takeaway: The slowest bug I ever fixed had nothing to do with algorithms or network latency. It was empty memory being carefully converted from one format to another, thousands of times over.

The Trip-Sharing App Nobody Asked For (But We Needed)

Right after grad school, some friends and I kept running into the same annoying problem. We all loved traveling, and we'd constantly ask each other things like "where did you stay in Lisbon?" or "send me that list of places from your Tokyo trip." The answers always came back as scattered texts or a Google Doc that someone forgot to share. So we built an app.

The idea was simple: a place where you could save the spots you've been to, organize them into collections, add friends, and share your trips with them. No more digging through group chats. We went serverless on AWS — DynamoDB for storage, Cognito for auth, the whole stack deployed automatically.

I ended up owning most of the backend plumbing. The part I'm proudest of isn't any single feature — it's the infrastructure I set up around the code. I wrote unit tests with Jest using mocked DynamoDB calls, wired up git hooks so tests ran automatically before any commit or push could go through, and built out a full CI pipeline in Azure Pipelines that spun up a VM, ran the test suite, and published coverage reports. None of that was required — we were just building this for fun — but I wanted to know what a real development workflow felt like end to end.

It taught me more about backend architecture, CI/CD, and working on a team than anything I'd done in school. It's also the project that made me become a software engineer — I came out of grad school with an electrical engineering degree, but building this app showed me that shipping software was what I actually wanted to do. And honestly, building something just because you and your friends wanted it to exist is the most fun way to learn.

AWS (DynamoDB, Cognito) · Serverless · Jest · Azure Pipelines · Node.js

From Signals to Software: What Adaptive Filtering Taught Me About Noisy Data

In grad school, I worked on multipath mitigation — the problem where radio signals bounce off buildings and terrain before reaching a receiver, arriving as a garbled mess of overlapping waveforms. GPS systems, passive radar, telecom — they all deal with this. I simulated the problem in MATLAB and used adaptive filters (LMS and NLMS) to recover the original clean signal from the noise.

The first approach — a basic two-tap LMS filter — didn't work. The weights oscillated and diverged instead of settling, and the error signal never died down. I spent a while tuning parameters thinking I had something wrong, but the filter just didn't have enough degrees of freedom to model the interference. Bumping it to eight taps helped significantly — the weights converged around 300 iterations and the error dropped to zero. But the real breakthrough was switching to NLMS, which normalizes the weight update by the input signal's energy. Even with just two taps, NLMS drove the error to near-zero where LMS couldn't. Then at higher sampling rates, LMS fell apart again — the weights started oscillating with no sign of convergence — while NLMS stayed stable. The lesson was that throwing more complexity at a problem (more taps, more iterations) doesn't always fix it. A fundamentally better approach at the algorithmic level can do more with less.

That pattern shows up constantly in software. I've hit the same dynamic building web apps — brute-forcing a solution with more code or more state when the real fix is rethinking the approach. Messy API responses, race conditions, state that won't settle — they're different problems on the surface, but the underlying shape is the same: noisy input, clean output needed, and a system that has to adapt.
